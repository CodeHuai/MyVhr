# 部门树递归查询（DepartmentWithChildren / 嵌套 select）

对应清单阶段 3 第 8 条。速查 `MyBatis-resultMap速查.md` §5 表格里"嵌套查询"一列的展开。
vhr 出处：`vhrserver/vhr-mapper/.../mapper/DepartmentMapper.xml`（2026-09-24 核对）

## 1. vhr 原文：两段 XML 互相咬合

```xml
<!-- DepartmentMapper.xml:12-14 -->
<resultMap id="DepartmentWithChildren" type="org.javaboy.vhr.model.Department" extends="BaseResultMap">
    <collection property="children" ofType="org.javaboy.vhr.model.Department"
                select="org.javaboy.vhr.mapper.DepartmentMapper.getAllDepartmentsByParentId"
                column="id"/>
</resultMap>

<!-- DepartmentMapper.xml:30-32 -->
<select id="getAllDepartmentsByParentId" resultMap="DepartmentWithChildren">
    select * from department where parentId=#{pid};
</select>
```

配套两处 Java：

- `Department.java:43`：`private List<Department> children = new ArrayList<>();`（字段初始化成空列表，不是 null）
- `DepartmentService.java:24`：`return departmentMapper.getAllDepartmentsByParentId(-1);`（service 就这一行）

## 2. 疑点：这个 collection 里什么映射都没有

和 Menus2（`MyBatis-resultMap速查.md` §4）不一样——它**不是嵌套结果**：内部没有 `<result>`、不指别的 resultMap，是自闭合的，全靠 `select` + `column` 两个属性。这是**嵌套查询**写法：children 的值不靠当前 SQL 的列拼出来，而是**映射到这一行时，另发一条 SQL 去查**。

逐属性：

| 属性 | 值 | 意思 |
|---|---|---|
| `extends` | BaseResultMap | 继承 6 列映射，只追加 children 的填法（同 Menus2 套路） |
| `property` | children | 要填的 Java 字段（`Department.java:43`） |
| `ofType` | Department | 集合元素类型，即 `List<Department>` 尖括号里那个 |
| `select` | ...DepartmentMapper.getAllDepartmentsByParentId | children 的值调哪条查询去拿 |
| `column` | id | 把**当前行的 id 列**的值传给那条查询，就是 `#{pid}` 接到的值 |

## 3. 运行时链条

1. service 调 `getAllDepartmentsByParentId(-1)` → SQL：`where parentId = -1`，查出所有根部门
2. 每行按 `DepartmentWithChildren` 映射：先按 BaseResultMap 填 6 列；发现 collection 带 `select` → 拿这行 id（比如 1）再发一条：`where parentId = 1`
3. **这条子查询的 resultMap 又是 DepartmentWithChildren**（第 31 行）→ 它查回的每行又触发下一层 `where parentId = 子部门的id`……
4. 终止：某层查回 0 行（叶子部门）→ 没有行可映射 → 不再触发下一条。叶子的 children 是空列表（字段初始化兜底），不是 null

递归不是 Java 写的——service 一行、无终止条件代码、无防 null 处理，是 **resultMap → select → 查询 → 同一个 resultMap** 这个环让 MyBatis 自己一层层查下去。层级任意深，这就是"部门树不定深"只能走这条路的原因（对照：菜单固定两层，Menus2 一条联查平铺就够）。

## 4. 关键认知：MyBatis 不知道自己在递归

它只认一条死规则——"映射到带 `select` 的 collection，就拿当前行的 column 值调那条查询，查回的行继续按那个查询的 resultMap 映射"。至于两段 XML 互相指、形成环，MyBatis 毫不知情也无需知情。**递归是这个环涌现出来的效果，不是任何一处代码写出来的功能。**

拆环实验（自证）：把 `getAllDepartmentsByParentId` 的 resultMap 改指 `BaseResultMap`，递归立刻消失，只查出一层平铺部门。整个魔法只在两行 XML 互相引用的那一下。

另一个角度：树的定义本身就是递归的（部门 = 自己 + 子部门列表），这个环就是数据结构定义在 ORM 映射上的直接投影。

## 5. 可自测点

- **SQL 条数**：嵌套查询 = 主查询 1 条 + 每个部门各 1 条（N+1）
- **何时执行**：vhr 的 `application.yml:22-24` 只配了 `log-impl`，没配 `lazyLoadingEnabled` → MyBatis 默认 false = 立即执行（非懒加载）→ 跑起来控制台按层级刷一串 SQL，对着日志看一遍就全通了
- **入口为什么传 -1**：根部门的 parentId 存的是 -1，从 -1 顺着 children 一层层下钻
